# How we handle errors in the public API

I get asked this in almost every onboarding, so here is the long version. This is about the handlers behind `api.example.com`, the ones customers call. It is not about the nightly batch jobs or the internal admin tools. Batch jobs should just crash loudly and page someone; nobody is on the other end waiting for a polite message.

The first thing to get right is who can do something about the error. If the customer sent us a date in the wrong format, that is theirs to fix, so we return a 400 and tell them which field and what we expected. Same when they try to create a webhook with a URL that isn't https, or ask for a page size over 200, or send an amount with three decimal places: 400 (or 422 for the semantic ones, we use 422 when the JSON parses but the values make no sense together, like an end date before the start date), plus the field name, plus what would have been valid. When they hit a rate limit it's a 429, and we always send `Retry-After`, because the thing they can do about it is wait and we should say how long.

If it's ours to fix, they get a 500 with a generic message and the request id, and that's all. The database being down, a null we didn't expect, a third-party call timing out (that one is a 502 or 504 actually, but same idea): there is nothing the customer can change in their request to make it work, so details don't help them. They only help an attacker. In 2023 we returned a raw Postgres error to a customer and it had a table name and part of a query in it. Another time a stack trace went out with an internal hostname. Another time the message included another tenant's account id, which was a reportable incident. So: no stack traces, no SQL, no hostnames, no internal ids, no library names or versions in any response body, ever.

There is one place where we deliberately tell the customer less than they could act on. If they ask for a resource that exists but belongs to another account, we return 404, not 403. A 403 confirms the thing exists. We'd rather a legitimate user be slightly confused than let someone enumerate ids.

Every error body has the same shape: `{ "error": { "code", "message", "request_id" } }`. Codes look like `ERR_<DOMAIN>_<REASON>`, for example `ERR_BILLING_CARD_DECLINED`. Customers write code against the codes, so a code never changes meaning once it has shipped. Messages are for humans and can be reworded any time. The request id is also sent as the `X-Request-Id` header.

Logging. Log the error once, in the top-level error middleware, with the request id. Please don't log it in the repository, then again in the service, then again in the handler. We had an outage where one failure produced eleven log lines across four layers and people thought there were eleven failures. Lower layers should throw (or wrap and rethrow with context), not log. Sentry gets 100% of 5xx and 10% of 4xx, because 4xx volume is mostly customers' bugs, not ours.

Retries. Our own outbound calls can be retried automatically only if doing it twice is harmless. GETs are fine. PUT and DELETE are fine. A POST that charges a card is not, unless we send an idempotency key, in which case it is. Sending an email is not. Enqueueing a job is fine because the queue dedupes on job id. When you aren't sure, don't retry; surface the failure.
